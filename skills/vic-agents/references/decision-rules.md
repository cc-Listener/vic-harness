# 决策规则

工作流以 [SKILL.md](../SKILL.md) 为准；本文件只解释是否需要委派和自定义角色。

## 先判断是否值得拆分

从 single-agent 起步。以下情况通常保持单代理：

- 任务局部、低风险，主会话能完整处理。
- 缺少目标、复现或项目事实；增加代理不能代替补足证据。
- 写入范围重叠，或交接与综合成本高于独立工作的收益。

仅在存在可说明的收益时升级：独立证据收集、专业职责、独立审查，或边界清晰的并行工作。不要逐项加分制造角色；同一收益只能支持实际需要的一份工作。

先盘点会自行派生子代理的既有 skill；已有同类审查能力时不重复建立 reviewer，除非明确列出不同证据面或未覆盖的质量门。只读取这些能力的公开说明，不复制外部 skill 文本或替它配置。

## 区分委派与自定义配置

- 先复用当前可用工具、技能和内置代理；需要委派不等于需要 custom agent。
- 只有稳定、重复使用的职责或配置差异值得落地为 `.codex/agents/<agent-name>.toml`。
- `main_session` 单独描述主会话；`active_agents` 仅列计划委派的子代理，不表示已经运行。
- custom agent 文件只作用于新启动的子会话，不能将主会话切换成该角色。
- `agent_count` 包含主会话；`max_concurrent_subagents` 和官方并发设置均不包含主会话。
- 角色数量按独立工作确定，默认总数控制在 1–4；超过 4 时说明收益和协调成本。普通升级无需额外审批，沿用当前授权与实际权限边界。

本次计划使用量与项目持久并发容量分别判断；使用量低于已有容量不构成修改全局上限的理由，可在本次计划/guardrails 限制使用量。每项持久变更须说明独立配置收益，角色文件数量也不等于实际并发。

## 按任务说明升级理由

| `project_mode` | 从单代理升级的依据 |
| --- | --- |
| `small-feature` | 存在需要独立审查的敏感路径或回归风险 |
| `medium-large-feature` | 有可独立交付、写入范围不重叠的工作 |
| `refactor` | 接口变化或跨模块回归需要独立验证 |
| `bugfix` | 复现、根因调查或修复审查形成独立工作 |
| `research` | 可独立获取和核对不同来源，综合收益超过交接成本 |
| `pr-review` | 第二份审查拥有不同证据面或明确检查范围 |

任务名称本身不决定代理数量。模型选择统一遵循 [model-policy.md](model-policy.md)，不要用更换模型代替确定职责。

## 最小落地

- 没有需要改变的全局设置或自定义角色时，允许零文件变更。
- 仅增量修改相关 `.codex/config.toml` 和 `.codex/agents/*.toml`；保留无关设置和代理。
- 配置字段以 [materialization-layout.md](materialization-layout.md) 和当前官方文档为准，不把摘要字段当成 TOML 配置。
- superpowers 状态为 `unknown` 时跳过可选 bridge，继续完成 TOML 工作；已有用户授权直接沿用。
- 生成文件本身不会启动子代理；本技能负责配置，不执行所配置的任务。

## 决策必须可核验

说明 multi-agent 是否必要、事实来源、`minimal_setup` 与有条件的 `enhanced_setup`、计划角色、实际文件变更及验证证据。保留 `evaluation`、`evidence_requirements` 和 `guardrails`；只有真实权限或高风险操作需要时才增加 `human_checkpoints`。
