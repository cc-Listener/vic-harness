# 增量刷新与零改动

分类之前读取；用写前已调查的根/app 事实集合检查现有覆盖，再决定是否需要增量维护。结果必须可审计。

## 最小资产与三分类

最小资产包括生效导航、项目地图、事实性约定、可定位组件文档和规范根事实合同。已确认的等价导航/人读文档优先原位复用；每个职责只有一个 canonical 入口。

| 模式 | 判定条件 | 产物策略 |
| --- | --- | --- |
| `bootstrap` | 缺核心资产，或仅有导航/局部文档/代理执行合同，尚无可用 bootstrap 层 | 补最小缺项，保留可复用资产 |
| `refresh` | 已有 bootstrap 层，但结构事实过期、分层错位、组件质量门不完整或 app-deep 子域缺项 | 只改受影响事实和入口 |
| `no-op` | 最小资产齐备、事实仍与证据一致、分层与组件质量门合格、所有需要的 app 子域已覆盖且无相关触发 | 完整文件树零写入，仅检查和回复 |

AGENTS 膨胀成治理手册，或导航/索引/bridge 复制项目事实，属于分层问题；受保护 legacy 层只报告，不能借 refresh 获得写权限。
即使 git status 为空，也须检查缺项、真实路径、import/export、组件符号索引与 app-level coverage。仅存在代理配置不能证明 bootstrap 完整。

## 触发与非触发

下列相关变化触发定向刷新：

- 顶层目录、workspace、package、app、service 边界新增/移除/重命名。
- 共享组件库、design system、SDK、wrapper 或 adapter 的入口、导出和推荐复用关系变化。
- lint/format/test/build/CI、贡献指南等规则入口变化。
- ownership、guarded path、review/release gate 的仓库事实变化。
- canonical 合同内容缺失/过期，导航与事实层冲突，组件定位缺项。
- [app-deep.md](app-deep.md) 的信号命中且子域合同缺失或过浅。

通常不刷新：边界内普通功能代码、小型 bug、沿用既有规范的测试修改、无关文案/纯内容更新。
缺失、失效、错层或无法定位才是覆盖缺口；发现更细的准确描述本身不构成刷新理由。
已有聚合 gate 能覆盖同一验证能力时保留其粒度；从实际脚本调用链核对工作目录、workspace/filter 范围和验证语义，不能仅凭名称认定覆盖。确认已覆盖的直接入口无需另增 VG；已有准确直接入口及 ID 同样保留，不为改用聚合而删除。新验证类型、原聚合漏包、调用语义变化或用户明确要求独立入口才可能构成真实缺口。其他关键定位场景仍须分别核对，不能用聚合验证覆盖来免除 PA/LI 缺项。
准确的等价包管理器命令写法、措辞或格式偏好不构成事实变化；例如 `npm test` 与 `npm run test` 语义等价时保留原准确写法，不仅为统一拼写刷新。已在 uncertainty 记录的依赖缺失/未验证 gate 是现状，不是每次运行的新触发。
其他 workflow 发现关键字段缺失/过期时允许定向补刷新。单纯代理配置变更不触发本 skill；外部明确指出项目事实冲突时才核对相关导航/事实证据。
M1 不调用尚未实现的 `--drift`，不依据 refresh-log 判断当前事实；确定性漂移能力留 T10。

## 增量与 no-op

- 保留准确的命名、顺序、ID、现有落位和无关内容；不要仅为美化重排整份合同。
- 已有有效 gate 执行证据仍适用时保留；no-op 不重新跑可能产生副作用的项目命令。
- 状态先按 artifacts 的“产物与覆盖”定义核对；`verified:false`、已知 uncertainty 或低信息仓库本身不等于缺少 bootstrap 层，也不自动触发 refresh。
- no-op 不要求状态字符串必须为 complete：partial 的已记录核心信息缺口在本次没有新证据时可保持原状态。仅改变状态表达不是刷新证据；新确认的事实或实际覆盖变化才触发更新。
- no-op 不创建目录、改权限、追加日志、更新日期或 commit 字段；也不写“运行摘要文件”。检查和回复输出放在仓库之外。
- 检查暴露权限内合同错误时，重新分类为 refresh 后修复，不能一边写文件一边声称 no-op。

## 回复证据

`refresh/no-op` 证据字段名及枚举只定义在插件根 [refresh-log.schema.yaml](../../../schemas/refresh-log.schema.yaml) 的 `$defs/vic-bootstrap`。按其中的运行模式、触发、影响/保留、未确认与深度/目标/落位字段组织回复，不在各 reference 维护另一份字段清单。
M1 证据仅在回复中提供，不生成日志条目，不为了模拟 M2 信封制造时间戳。触发写具体仓库路径/缺项，受影响项写实际文件；no-op 明确没有变更，保留项说明核对过的入口。
app-deep 时解释为何采用 `root-docs` 或沿用 `app-local-docs`；不涉及 app 时目标为空，仍给出根层落位依据。执行与检查有未完成项时直接说明。
