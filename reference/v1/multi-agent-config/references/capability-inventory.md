# 能力盘点与增量刷新

先盘点真实能力，再决定角色。每类能力明确区分 `available`、`missing_but_relevant`、`planned_additions`；空列表使用 `[]`，不把计划安装或父会话可见的能力直接当作子代理已具备。

## 记录范围

| 类别 | 记录内容 | 边界 |
| --- | --- | --- |
| `tools` | 会改变执行能力的终端、文件读写、搜索、测试、浏览器等 | 合并同义项，例如 `ripgrep` 归为 `search` |
| `skills` | 当前可用且影响流程或产出的技能 | 区分技能存在、可被当前角色读取与本次必须使用 |
| `mcp` | 实际可用的 MCP 服务及相关连接器能力 | 是能力来源，不是代理运行时；不要假定已获全部外部操作权限 |
| `runtimes` | `current-session` 与 `isolated-child` | 是执行与上下文边界，不是工具列表 |

对关键能力写明发现来源和不确定性。模型可用性及继承规则见 [model-policy.md](model-policy.md)。

这里的 `runtimes` 只描述代理执行与上下文边界；Python、Node 等解释器作为本地工具能力记录，不混入 `runtime_class`。

## 运行时与权限

- `current-session` 对应主会话；`isolated-child` 对应子会话的独立上下文，不代表独立文件系统或独立工作副本。
- 并行写入前明确每个角色的 `write_scope`；共享目录中的改动可能立即被其他代理看到。
- 不假定子代理继承主会话全部临时信息、工具状态或连接器权限；交接应给出必要文件、证据和约束。
- agent 文件中的 `sandbox_mode` 可能被父运行时的权限设置覆盖；外部连接器权限独立于本地文件系统沙箱。
- 若任务必须依赖真实只读或其他强制限制，先验证运行时实际权限；仅有角色说明不足以声称隔离已生效。

## 约束如何落地

按角色需要在摘要或 `developer_instructions` 中描述：

- `preferred_tools`、`allowed_tools`、`forbidden_tools`
- `required_skills`、`optional_skills`
- `required_mcp`、`optional_mcp`
- `runtime_class`、`write_scope`

这些是执行建议和职责约束，不是官方 TOML 权限字段，也不能强制禁止工具调用。只列实际必要的约束；真实权限由当前运行时、官方支持的配置与连接器授权共同决定。不要把上述摘要字段直接写入 agent TOML。

## 能力变化后的刷新

1. 更新受影响能力，去重并保留可用性证据。
2. 找出依赖该能力的角色及验证方式。
3. 只刷新相关摘要、角色指令和官方支持的配置字段。
4. 仅在变化影响职责、可安全并行性、验证质量或运行时边界时重新判断角色组合。

报告能力变化、实际修改和仍缺少的证据。角色组合无需变化时直接说明，不为新增工具额外创建代理。
